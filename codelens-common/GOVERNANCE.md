## 程序法：变更治理5条

### 1. 变更通知流程
- 改了 codelens-common → **必须**飞书群发通知，附 diff 摘要
- Hermes 收到通知后 **48h 内**完成同步
- 超时未同步 → 自动标红，一致性验证暂停

### 2. 破坏性变更否决权
- **非破坏性变更**（新增字段、放宽阈值）→ 喵呜直接推，通知 Hermes
- **破坏性变更**（删字段、收紧阈值、改接口签名）→ 喵呜提出，Hermes 48h 内确认可执行，**默默认可**才合并
- Hermes 有**延期否决权**：在确认期内说"我跑不了"，改动暂缓

### 3. 第三方依赖准入
- codelens-common 新增依赖 → **默默审批**，确保两端都能用
- codelens-common 零 IntelliJ 依赖（铁律）
- 语法边界：**以 Hermes 端最低 JDK 为上限**，common 代码 ≤ JDK 1.8 语法

### 4. 变更链追踪
每个 codelens-common 变更必须在 SYNC_VERSION 中声明影响范围：

```
SYNC_VERSION: 2026-05-17-v1
IMPACT: SCHEMA_CHANGE
```

| 类型 | 含义 | 谁声明 | 谁把关 |
|------|------|--------|--------|
| `PROMPT_ONLY` | 只改了 prompt 文本，不影响代码 | 喵呜 | 默默 |
| `SCHEMA_CHANGE` | Schema 变了，校验器和 UI 都要跟 | 喵呜 | 默默 |
| `LOGIC_CHANGE` | 校验逻辑变了，两端结果可能不一致 | 喵呜 | 默默 |
| `BREAKING` | 接口/签名变了，另一端必须同步才能跑 | 喵呜 | **默默卡** |

### 5. 紧急修复流程
- **紧急修复**：直接改 + 飞书群通知 + 事后补版本号
- 紧急定义：**影响分析结果正确性**的问题
- 非紧急：走正常流程
- 拍板人：**默默**（定义什么算"紧急"）

## 四条开发原则

1. **Think Before Coding** — 先列假设再动手
2. **Simplicity First** — 字段必须有消费方
3. **Surgical Changes** — 一次只改一个关注点
4. **Goal-Driven Execution** — 必须有可验证的成功标准

---

## 仓库策略

**3模块1.5仓库：**
- `codelens-java/`（CLI端 + common 寄生）
- `codelens-plugin/`（插件端）

**拆仓触发条件：** common 文件数 > 10 **或** 手动同步出错 > 3 次

拆仓后：common 仓库独立，变更通知、破坏性变更追踪走 PR + review。

## 执行机制

| 层级 | 卡口 | 触发时机 |
|------|------|---------|
| 结构 | common=公共合同，改了必须通知 | 任何common变更 |
| 任务 | Action Item 声明拍板人+范围+成功标准 | 创建任务时 |
| 合并 | 拍板人确认；对齐类无确认不合并 | Code Review时 |

## 同步机制细则

### 版本号规则
格式：`YYYY-MM-DD-v序号`
改才升号，不改不动。升号由维护方负责。

### 插件端同步方式
- 保留副本 + 版本号标注
- 收到版本更新通知后覆盖同步
- 不删代理有副本，只覆盖
- 覆盖后更新自身文件的 SYNC_VERSION 注释
