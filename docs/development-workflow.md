# CodeLens 开发工作流

> 2026-05-21 定版
> 维护人：喵呜
> 默默确认后生效

---

## 核心原则

**先文档后代码，先测试后开发。** 每一步有产出、有据可循，不靠人记。

---

## 插件端流程（嗷呜 + Cline）

```
1. 嗷呜 写需求文档    → docs/requirements/
2. Cline 读需求文档   → 确认理解
3. 嗷呜 写测试用例    → docs/test-cases/
4. Cline 写代码       → 按需求文档和测试用例做
5. Cline 自测         → 跑全量测试
6. Cline 提 PR        → 分支提交，CI 通过
7. 嗷呜 代码审查      → 有问题打回，没问题合并
8. 闭环               → 通知默默
```

## CLI 端流程（喵呜 + Claude Code）

```
1. 喵呜 写需求文档    → docs/requirements/（只写目标+验收标准，不写实现方案）
2. 喵呜 写测试用例    → docs/test-cases/（基准测试也算）
3. Claude Code 读需求 → 建分支（feature/REQ-XXX），自主实现
4. Claude Code 自测   → mvn test + mvn package
5. Claude Code 提 PR  → 推送分支，等待审查
6. 喵呜 代码审查      → 看实现是否合理，有问题打回，没问题合并到 main
7. 喵呜 打 tag        → 合并后打 tag，JitPack 构建
8. 喵呜 验收          → 验证 JitPack 绿色 + 基准测试
9. 闭环               → 通知默默
```

**关键变化**：
- 需求文档只写"做什么"和"怎么验证"，不写"怎么改"
- Claude Code 在 feature 分支上自主实现，不直接改 main
- 喵呜审查后才合并打 tag，防止污染主分支

## 涉及 common 变更时的协作流程

当需求同时涉及 common 和插件端时：

```
1. 嗷呜 写需求文档（🔵 插件端部分）
2. 喵呜 补充需求文档（🟠 common 部分）
3. 默默 评审 → 两部分都确认才开干
4. 喵呜 先做 common 变更 → 打 tag → JitPack 构建
5. 嗷呜 升级依赖 → 做插件端部分
6. 各自验收 → 通知默默
```

**顺序很重要**：common 先行，插件端依赖 common 的新版本。

## 需求文档模板

```markdown
# 需求标题

> 编号：REQ-XXX
> 优先级：🔴 P0 / 🟡 P1 / 🟢 P2
> 端：🔵 插件端 / 🟠 common 变更 / 📋 Schema

## 目标
要解决什么问题，达到什么效果

## 变更范围
- 涉及哪些模块/文件（粗粒度即可，不指定具体行号）
- 影响面

## 验收标准
- [ ] 具体的可验证条件（这是最重要的部分）

## 依赖
- 前置条件
- 关联需求

## 约束（可选）
- 技术限制（如 JDK 1.8、零 IntelliJ SDK 依赖等）
- 已知风险或需避免的方案
```

**注意**：需求文档不写实现方案。Claude Code / Cline 自主决定怎么实现，审查环节验证实现合理性。

## 管理原则（2026-05-22 复盘定版）

### 管理者角色
- **做**：定方向、定验收标准、审结果
- **不做**：帮AI想代码怎么写、纠正prompt细节、每步参与纠正

### 三遍定律
同一个问题重复三次，停下来复盘方向，不继续硬推。适用所有人（默默、喵呜、嗷呜）。

如果AI在同一个模式上反复犯错，可能不是AI的问题，是方向或分工方式有问题。

### 对话式需求确认
```
默默抛方向 → 主管追问 → 来回确认 → 默默说"对" → 落需求文档 → 默默扫一眼 → 开干
```
文档的角色：不是"向默默输送信息"的工具，而是"把默默确认过的东西固化下来"。

### 审查优先级

| 优先级 | 审查内容 | 说明 |
|--------|----------|------|
| 🔴 P0 | 安全性 | API Key泄露、文件越权、敏感信息暴露 |
| 🔴 P0 | 影响范围 | 改了哪些模块？其他功能会被影响吗？ |
| 🟡 P1 | 逻辑正确性 | 功能是否按需求文档实现？边界条件覆盖了吗？ |
| 🟢 P2 | 代码规范 | 命名、注释、风格——不阻塞合入 |

审查门槛：P0-P1没问题 → P2问题评论但不阻塞合入。

### 跨端边界铁律
1. **谁的地盘谁做主** — 另一个主管不得干预
2. **跨端走契约** — common是契约，改契约需提需求到 `common-change-tracker.md`
3. **越界即打回** — 默默看到越界行为直接指出
4. **协作性越界 vs 破坏性越界**：
   - 协作性（顺手修bug）：建`[cross-team]`前缀分支 → 该端主管评审 → 合入 → 通报
   - 破坏性（改逻辑结构）：打回，重做

### 需求变更流程
```
默默说"方向变了" → 停下当前开发 → 对话确认新需求 → 评估当前进度
  → 小改：写进需求文档+测试用例 → 单独提小任务 → 接着做
  → 推翻重来：重新走需求流程（对话确认→落文档→评审→新建分支→开发）
```

### 验收机制
- **日常验收**：主管审代码质量 → 默默做产品级验收（看效果不看代码行）
- **里程碑交叉评审**：嗷呜审CLI端关键改动 / 喵呜审插件端 / 默默审方向
- **发布验收**：默默确认需求全走完 + 基准测试通过 + 文档更新 → 再发版

## 反面教训

### v0.2.4/v0.2.5 C6 deps 过拟合修复失败（2026-05-21）

- **问题**：连续3次修改prompt（v0.2.4脚注→v0.2.5扩展示例+硬规则29），C6 deps仍为1
- **根因**：不是prompt的问题，是struct上下文只输出1个字段（其余在父类），LLM被"事实"级信号误导
- **如果按流程**：第2次失败后应停下来复盘根因，而不是继续在prompt层面加码
- **教训1**：测试用例先于开发（C6 deps≥20，第一轮就能发现方向不对）
- **教训2**：同一问题修3次无效，必须停下来复盘——**方向可能就是错的**
- **教训3**：先单文件验证→确认有效→再全量回归，不浪费资源

---

### 三次失败复盘规则（2026-05-21 新增）

**同一问题修3次仍未解决，必须停下来复盘。** 不允许第4次继续在原方向加码。

复盘清单：
1. 问题定位是否正确？（可能不是你以为的那个原因）
2. 修复方向是否正确？（可能换方向比加码更有效）
3. 是否有更底层的因素？（如数据源误导、架构缺陷等）
4. 是否需要换验证方式？（全量测试→单文件快速验证）
